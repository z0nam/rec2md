# 기능 검토: 화자 DB · 맥락 보정 · 회의록 생성 (2026-10-30)

세 기능 모두 "클로바노트와 견줄 만한가"가 기준이다. 클로바노트는 전사 품질과 앱 편의성에서 앞서지만, 이 세 가지는 약하거나 아예 없다. 그래서 여기서 차별점을 만든다.

| | 클로바노트 | rec2md 목표 |
|---|---|---|
| 화자 실명 | 매번 손으로 이름 지정 | 등록된 목소리는 자동으로 실명 부여 |
| 고유명사 | 키워드 등록 정도 | 회의 시리즈마다 쌓이는 용어집 + 낮은 확신 구간만 골라 맥락 보정 |
| 결과물 | AI 요약(앱 안) | 회사 양식 회의록(hwpx·docx 등) + 클로바식 녹취록, pdf·png 내보내기 |

공통 원칙
- 목소리 임베딩·용어집·회의록 원본은 모두 개인 데이터다. `~/.config/rec2md/` 아래나 출력 폴더에만 두고 레포에는 넣지 않는다. 퍼블릭 레포에는 합성 음성 픽스처와 빈 양식만 둔다.
- CLI가 기계적인 부분(임베딩, 매칭, 렌더링)을 맡고, 판단이 필요한 부분(이름 확정, 애매한 단어 보정, 회의록 문장)은 에이전트(스킬)가 맡는다. 1단계와 같은 분업이다.

## A. 화자 목소리 DB와 자동 태깅

### 가능성: 높음
- pyannote community-1 파이프라인은 화자분리를 하면서 클러스터마다 대표 임베딩(`speaker_embeddings`)을 함께 내놓는다. 그래서 추가 연산이 거의 없다.
- 같은 사람이라도 마이크와 거리에 따라 임베딩이 흔들린다. 그래서 한 사람당 임베딩을 여러 개(녹취별로) 저장하고 최댓값으로 매칭한다.
- 한 녹취 안에서 두 클러스터가 같은 사람에 붙지 않도록 헝가리안 매칭(1:1)을 쓴다. 다만 pyannote가 한 사람을 둘로 쪼갠 경우(파일럿 위원회 녹취: 10 vs 9)도 있으므로, 둘 다 임계값을 넘으면 "같은 사람 후보"로 표시한다.

### 설계
- 사이드카: 전사 때 `<이름>.voices.npz`(클러스터 라벨 → 임베딩, 발화 길이)를 출력 옆에 저장한다. 그래서 나중에 녹취록을 확정한 뒤 다시 돌리지 않고 등록할 수 있다. 이 파일은 gitignore.
- DB: `~/.config/rec2md/voices/voices.db`(sqlite). 테이블은 `person(id, name, note)`, `embedding(person_id, vec, source, seconds, created)`. 생체정보이므로 파일 권한은 600.
- CLI
  - `rec2md voices enroll <segments.json> --map "화자3=홍길동,화자5=김철수"`: 사이드카에서 해당 클러스터 임베딩을 꺼내 등록한다. 발화가 30초 미만인 클러스터는 거절한다(임베딩 품질).
  - `rec2md voices list | rename | forget <이름>`: forget은 그 사람의 임베딩을 전부 지운다.
  - `rec2md voices match <segments.json>`: 이미 전사한 파일에 다시 매칭한다.
  - 전사(`rec2md <audio>`) 때 DB가 있으면 자동으로 매칭한다. 끄려면 `--no-voices`.
- 결과 표기
  - segments.json의 `meta.speaker_names = {"화자3": {"name": "홍길동", "score": 0.81}}`처럼 라벨은 유지하고 이름은 따로 단다.
  - raw.md는 `홍길동(화자3)`처럼 쓴다. 점수가 경계 구간(임계값 ± 0.05)이면 `홍길동?(화자3)`로 쓴다.
- 스킬 연동: 에이전트가 녹취록을 확정하고 사용자가 화자 매핑을 승인하면 `voices enroll`을 실행해 DB를 키운다. 처음 몇 건만 사람이 확인하면 이후에는 자동으로 붙는다.

### 검증 (임계값을 정하는 근거)
- 정답 확보: 클로바 txt의 화자명은 사용자가 손으로 붙인 실명이다. `scripts/compare.py`의 그리디 매핑으로 우리 클러스터와 클로바 실명을 대응시키면 정답 라벨이 자동으로 생긴다.
- 방법: 녹취 N건을 leave-one-out으로 평가한다. 나머지로 등록하고 하나를 매칭해 정밀도와 재현율을 계산한다. 같은 사람이 여러 녹취에 나오는 조합(본인, 반복 회의 참석자)이 핵심이다.
- 목표: **오태깅(엉뚱한 실명) 1% 미만**을 먼저 맞춘다. 미태깅(`화자N`으로 남음)은 허용한다. 틀린 이름이 이름을 안 붙이는 것보다 훨씬 해롭다.

## B. 회의 맥락에 맞춘 애매한 단어 보정

### 가능성: 중간〜높음
남은 오인식의 대부분은 고유명사, 기관·사업명, 신조어다(파일럿 결과). 일반 어휘 오류는 적다. 그래서 "무엇이 맞는지 아는 사전"만 있으면 상당 부분 고칠 수 있다.

### 설계: 두 겹
1. **전사 단계(편향)**: 용어집을 Whisper `initial_prompt`로 청크마다 넘긴다. 이렇게 하면 표기가 맞는 쪽으로 기운다.
   - 위험: 프롬프트 문구가 무음 구간에 그대로 튀어나오는 환각이 생길 수 있다. 그래서 길이를 제한하고(약 200토큰), 프롬프트 문구와 똑같은 출력은 기존 환각 필터에 추가한다.
   - 효과와 부작용은 실측으로 정한다(아래 검증). 효과가 없으면 2만 쓴다.
2. **후처리 단계(보정)**: CLI는 **보정 후보만** 뽑고, 실제 교정은 에이전트가 한다.
   - 후보: 단어 확률이 낮은 구간, 그리고 용어집 항목과 자모 편집거리가 가까운 구간.
   - segments.json에 `low_conf` 구간을 남긴다. 지금은 단어 정보를 버리고 있으므로 이 정보를 보존해야 한다.
   - 에이전트는 후보 구간만 고친다. 근거(용어집 항목, 같은 회의 다른 발언, 안건 문서)를 달고, 확신이 없으면 `[?]`. 전체를 다시 쓰지 않게 해서 LLM의 과잉 교정을 막는다.
   - 결과는 `<이름>.corrections.json`(원문, 수정, 근거, 타임스탬프)로 남겨 diff로 볼 수 있게 한다.

### "회의 세션 연계" = 시리즈
- `--series <이름>`(예: `○○위원회`)을 주면 `~/.config/rec2md/series/<이름>/`의 맥락을 쓴다.
  - `glossary.txt`: 용어·인명·기관명. 한 줄에 하나씩 쓰고, `오인식 => 정답` 형식도 받는다.
  - `attendees.txt`: 참석자 명단. A의 화자 후보 축소에도 쓴다.
  - `docs/`: 안건, 발표자료, 이전 회의록(텍스트로 추출해 둔 것).
- 회의가 끝나고 에이전트가 확정한 교정은 시리즈 용어집에 쌓인다. 그래서 회차가 지날수록 좋아진다. 클로바노트에는 없는 구조다.
- `--context <파일...>`: 시리즈 없이 이번 회의 자료만 줄 때 쓴다. 위시리스트의 "회의 메모 보정"(`--notes`)도 이 경로로 합친다. 메모는 맥락 자료이면서 보정 대상이다.
- 클로바 txt 3번째 줄(참석자 목록)과 파일명 패턴에서 시리즈 이름과 참석자를 자동으로 제안한다.

### 검증
- 같은 위원회의 여러 회차 녹취로 평가한다. 고유명사 목록(사람이 확인한 정답 30〜50개)의 적중률을 보정 전후로 비교하고, 클로바와도 비교한다.
- 일반 CER이 나빠지지 않는지(과잉 교정) 함께 본다.

## C. 회의록 자동 생성과 다형식 내보내기

### 가능성: 높음 (가장 기계적)
- 녹취록은 이미 있다. 회의록은 같은 내용을 **양식에 맞춰 구조화**한 것이다.
- 핵심은 형식마다 따로 짜지 않고, **회의록 JSON 하나를 렌더러 여러 개가 받는 구조**로 만드는 것이다.

### 설계
```
녹취록.md ──(에이전트)──▶ <이름>.minutes.json ──(rec2md render)──▶ md / html / docx / hwpx
                                                              └──▶ pdf / png (export)
segments.json ──(rec2md render --kind transcript)──▶ 클로바식 녹취록 md / txt / docx / hwpx / html
```
- **회의록 스키마**: `rec2md.minutes`(dataclass)와 `docs/minutes-schema.md`. 에이전트는 이 스키마로 JSON을 쓰고, 렌더러는 이 스키마만 본다.
- **양식(template)**: `rec2md render --template <이름>`
  - 기본 내장 `kr-standard`: 국내 기관 회의록의 공통 골격(회의일시, 장소, 참석자, 안건, 회의내용, 결정사항, 향후 일정). 형식마다 하나씩 둔다.
  - 회사 양식 `ji`: 제주연구원 회의록 표(회의일시·연구자·작성자 / 참석자 / 회의장소 / 회의안건 / 회의내용, 내용은 `1. 소제목` → `▶ 소항목` → `- 내용` 3단). 실제 hwpx 양식 파일은 사용자 설정 폴더(`~/.config/rec2md/templates/ji/`)에 두고, 레포에는 필드 매핑만 둔다.
  - 사용자 양식: `~/.config/rec2md/templates/<이름>/`에 `template.toml`(필드 → 위치 매핑)과 형식별 원본(`form.hwpx`, `form.docx`, `page.html.j2`)을 넣으면 된다.
- **형식**
  - md, html: Jinja2 템플릿. html은 인쇄용 CSS를 포함해 pdf와 png의 원천으로 쓴다.
  - docx: `python-docx`. 사용자 양식이 있으면 `docxtpl`로 채운다.
  - hwpx: hwpx는 zip 안의 XML이다. 양식의 표 칸을 이름(누름틀이나 표지 텍스트)으로 찾아 채운다. hwp-agent의 `form fill`과 같은 방식이다. 의존성을 피하려고 최소한의 채우기는 rec2md 안에 두고, hwp-agent가 있으면 그것을 쓴다.
  - 추가 후보: `txt`(클로바 txt와 같은 배치. 기존 클로바 사용자의 습관과 비교 도구 호환), Google Docs는 개인 스킬(gdoc-push) 쪽에서 처리하고 레포 범위 밖.
- **내보내기(export)**: `--export pdf,png`
  - html → pdf·png: 헤드리스 Chrome(`--print-to-pdf`, `--screenshot`). 없으면 WeasyPrint.
  - docx → pdf: LibreOffice(`soffice --headless --convert-to pdf`).
  - hwpx → pdf·png: rhwp(`export-svg`)가 있으면 svg → png·pdf. 없으면 "한글에서 PDF 저장" 안내.
  - png는 쪽마다 한 장(`<이름>.p1.png` …).
- **클로바식 녹취록**: 제목, 일시·길이, 참석자 줄, 그 아래 `이름 00:00` + 발화 블록. 클로바노트에서 넘어오는 사람이 익숙한 모양이다.

### 검증
- 실제 회의 2건으로 `ji` 양식 hwpx를 만들어 한글에서 열리는지 확인한다(rhwp 렌더 + 사람 확인).
- 사용자가 실제로 제출한 회의록과 나란히 놓고 항목 누락을 확인한다.
- 형식마다 골든 파일 테스트를 둔다(합성 회의록 JSON → 렌더 → 텍스트 추출 비교).
