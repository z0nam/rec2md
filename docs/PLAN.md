# 녹취록 스킬 `rec2md` — 1단계 계획 (영상→슬라이드는 2단계)

## Context
- 현재 회의·전화 녹취를 네이버 클로바노트로 처리 중. 업로드, 다운로드, 복사·붙여넣기를 손으로 해야 해서 번거로움.
- 클로바노트 개인판은 API가 없어 자동화가 불가능함. 웍스판 Team 요금제(월 10.8만원)에만 비공개 API가 있음.
- 한국어 화자분리 녹취와 요약을 해주는 Claude Code 스킬·MCP 서버는 사실상 없음.
  - 가장 가까운 것은 openai/skills `transcribe`(gpt-4o-transcribe-diarize). 요청당 25MB 제한이 있고 미국 클라우드를 씀.
- 그래서 직접 만드는 작은 CLI와 스킬로 간다. 부품은 이미 성숙해 있고, 묶어주는 부분만 만들면 됨.
- 같은 녹취 모듈을 2단계(컨퍼런스 영상→슬라이드+노트)에서 재사용함.

## 실행 환경 (2026-10-16 결정)
- **개발 거점은 studio(Mac, `~/dev/rec2md`)** — ~/dev 프로젝트 지도·라우팅 규약이 있는 메인 작업공간이고, local 엔진(mlx)이 네이티브로 돈다. ffmpeg·uv·claude 설치돼 있음.
- **namun-ji(Windows)**: 녹음기(E:\REC_DIR)가 꽂히는 곳. GTX 1060 3GB라 로컬 STT 부적합. CLI를 `uv tool install`로 설치해 녹음기 파일을 studio로 보내는(`--remote studio`) 입구로 씀. 클라우드 엔진도 여기서 직접 호출 가능. ffmpeg는 winget으로 설치 완료(9.0.2).
- **local 엔진**: studio에서 `mlx-whisper` large-v3(또는 turbo) + pyannote community-1(MPS). 외부 전송 없음, 추가 비용 없음 → **기본 엔진**.
- E:는 녹음기 마운트라 상시 접근 불가 → 개발용 샘플은 `samples/`(gitignore)에 복사해 둠.

## 접근
엔진을 플러그인처럼 갈아끼우는 Python CLI로 만들고, Claude가 정리와 요약을 맡는다.

```
rec2md <audio> [--engine local|rtzr|clova]  # 기본 local [--call] [--speakers N] [--remote studio]
  1. ffmpeg로 정규화 (16kHz mono wav)
  2. 엔진 호출 → 공통 스키마 segments.json
     [{start, end, speaker, text}]
  3. raw transcript .md 작성 (타임스탬프 + 화자 라벨)
→ SKILL.md 지시로 Claude가 후처리:
     화자 이름 매핑(대화에서 추론하거나 사용자에게 확인), 군더더기 정리, 문단화
     → 녹취록.md + 요약(개요 / 논의사항 / 결정사항 / 할일)
```

### 엔진
| 엔진 | 용도 | 비고 |
|---|---|---|
| `local` (**기본**) | 백로그·일상 녹취 전부 | studio에서 mlx-whisper + pyannote. VAD(무음 구간 필터링)로 무음 구간 환각 방지. 비용·시간 제한 없음 |
| `rtzr` | 품질 기준점·보조 | 계정당 무료 10시간을 파일럿 비교에 사용. 이후 시간당 약 1,000원. `domain=CALL`(전화), 화자분리, 4h/2GB |
| `clova` | 품질 기준점·보조 | CLOVA Speech 장문 API(클로바노트와 같은 계열 엔진, 클로바노트 앱 한도와는 별개). NCP 가입·결제 필요, 단가는 콘솔 확인 |

- `--remote studio` (2026-11-04 동작, `src/rec2md/remote.py`): Windows에서 `scp`로 원본을 studio `~/.cache/rec2md/remote/<job>/in/`에 보내고, `nohup`으로 원격 rec2md를 띄운 뒤 짧은 ssh로 상태·로그를 확인하다가 `out/`을 회수하고 job을 지운다.
  - ssh가 끊겨도 원격 처리는 계속되고 `rec2md remote fetch <job>`으로 나중에 받는다. 원격 job끼리는 flock으로 한 번에 하나, 락 밖 rec2md는 경고만.
  - 디스크: 올리기 전 여유 ≥ 크기×3 확인. 원본(in/)은 성공·실패 모두 끝나자마자 지우고, 실패 job은 로그·상태만 7일 보관, 받지 않은 성공 결과는 fetch까지 보관.
  - `--series`·목소리 DB는 studio 것, `--context` 파일은 같이 올린다. `batch --remote`는 파일마다 job 하나(상태 파일은 로컬).
  - Windows 실측(2026-11-04, namun-ji → studio, 합성 음성 16초): 단일 17초, `batch --remote` 1개 done. 이때 찾은 것: ① Windows ssh.exe는 stdout이 파이프면 원격 명령이 끝나도 종료하지 않는다 → 출력을 임시 파일로 받는다(`remote.run_captured`). ② Windows 기본 설치엔 numpy가 없어 batch(trim)가 못 돈다 → `batch` extra. ③ ssh로 들어온 세션의 프로세스는 winget `Links\ffprobe.exe` 심링크를 못 따라간다(WinError 448) → `audio._require`가 심링크 대상을 직접 찾는다.
  - 함정(실측): namun-ji 기본 셸은 PowerShell 5.1이라 `&` 연결이 안 되고, ssh를 `-n` 없이 부르면 stdin을 기다리며 멈춘다. studio 비대화형 ssh의 PATH는 `/usr/bin:/bin:/usr/sbin:/sbin`뿐이라 rec2md는 `~/.local/bin/rec2md` 경로로 부르고, 원격 쪽에서 `/opt/homebrew/bin`(ffmpeg) 등을 PATH에 붙인다. 한글·공백 파일명은 scp 양방향 그대로 유지됨.
- **방침: 로컬 우선, 클라우드는 기준점·보조** (2026-10-16 변경). 처음엔 클라우드 우선이었으나, studio가 로컬 엔진을 충분히 돌릴 수 있고 클라우드 무료 한도(RTZR 계정당 10시간)로는 188시간 백로그를 감당할 수 없어 뒤집음.
- 클라우드는 (1) 파일럿에서 로컬 품질을 재는 기준점, (2) 로컬이 크게 밀리는 유형(전화·잡음 현장 등)에 한해 선택 사용.
- 파일럿: 같은 녹취 2〜3건(회의 1, 전화 1)을 local과 rtzr(무료 한도 내), 가능하면 clova로 돌려 비교. 로컬 처리속도(실시간 대비 배수)도 실측.

### 일괄 처리 (기존 녹취 백로그)
- `E:\REC_DIR` 실측(2026-10-16): MP3 167개, 10.1GB, **총 188.5시간**, 전부 128kbps. 파일별 목록은 `local/backlog-durations.tsv`(gitignore — 파일명에 인명·회의명 포함).
  - 30초 미만 빈 파일 15개 → 건너뜀.
  - **4시간 초과 8개**(최장 360분). local은 6시간까지 한 번에 처리한다(아래 "긴 녹음 메모리 실측"). 클라우드는 RTZR 4h 제한이 있어 분할이 필요하지만 이번 범위가 아니다.
  - `YYYYMMDD_주제.MP3`로 이름 붙인 파일과 `REC000NN.MP3`가 섞여 있음. `REC000NN`은 녹음기 시계가 없어 수정일 1601년 → 날짜·주제는 내용에서 추론.
- `rec2md batch <dir> [--dry-run] [--min-sec 30] [--out <dir>] [전사 옵션 …]` (`cmd_batch.py`, 이슈 #10)
  - 대상은 `<dir>` 바로 아래의 mp3·m4a·wav·mp4·mov(대소문자 무시, 재귀 없음). 전사 옵션은 `rec2md <파일>`과 같다.
  - `--dry-run`: ffprobe로 파일별 길이와 판정(처리·재시도·이미 처리·짧음·분할 필요·길이 확인 실패), 처리 대상 총 길이, local 예상 처리시간(실시간 12배 가정)을 표로 출력.
  - 상태 파일 `<out>/.rec2md-state.json`(`{파일명: {status: done|failed, sec, source, error}}`): done은 건너뛰고 failed는 다시 시도. 한 파일이 실패해도 다음으로 넘어가고, 실패가 있으면 종료 코드 1 → 같은 명령으로 재개.
  - 출력 이름이 겹치는 파일(같은 폴더의 `회의.mp3`·`회의.wav`, 또는 같은 출력 폴더를 다른 원본이 이미 씀)은 처리하지 않고 "이름 겹침"으로 표시, 끝에 종료 코드 1.
  - 출력은 기본 `<dir>/_transcripts/`.
  - **`--language auto`** (`langid.py`, `rec2md <파일>`·batch 공통, 2026-11-05): 백로그를 ko로 고정했더니 영어 녹음이 한글로 전사됐다.
    - 말소리 구간(화자분리, `--no-diarize`면 파일 전체)을 이어 붙인 축의 처음·중간·끝 30초 창마다 Whisper 언어 판별 확률을 보고, 그 창을 언어를 정하지 않고 받아 적은 글자(한글·라틴 비율)로 교차 확인한다. 창 판정을 모아 ko / en / mixed / silent로 정한다.
    - mixed·silent는 ko로 전사하고 `meta.language_detect`(판정, 창별 언어·확률)에 남긴다. 확실한 창(확률 0.6 이상)이 있으면 그보다 약한 창은 뺀다.
    - 근거: 같은 방식(시각 기준 처음·중간·끝 창)으로 백로그 162건을 판별해 ko 133 / en 8 / mixed 18 / silent 3. 처음·끝의 낮은 확률 en 창은 대부분 잡음 오판이었다. 약한 창을 빼는 기준을 적용하면 mixed 18건 중 8건이 ko가 되고 en 8건은 그대로다. 말소리 구간 기준 창은 이 잡음 창을 더 피한다.
    - `batch --dry-run --language auto`는 소리 크기로 남긴 구간에서 미리 판별해 "언어" 열을 보인다(mlx 필요, 없으면 건너뜀). 실제 전사 때 다시 판별한다.
    - 기본값은 ko 고정 그대로다. 백로그 대부분이 ko이고, 판별은 녹음마다 모델 호출 6번(창 3개 × 판별·받아 적기)을 더한다. 남은 문제는 앞부분만 한국어 소개이고 본문이 영어인 녹음이다. 이런 녹음은 mixed가 되어 본문도 한글로 전사된다(다음: 구간마다 언어 판별).
  - 긴 녹음은 대부분 녹음기를 안 꺼서 생긴 무음이다 → 전사 전에 **긴 무음을 잘라낸다**(`trim.py`, `rec2md <파일>`·batch 공통, `--no-trim`으로 끔). 1초 단위 dBFS로 임계값(잡음 바닥 하위 20% + 15dB, -45〜-30dB로 묶음)을 넘는 초가 1분 창의 10% 이상이면 말소리 창, 그 사이 5분 이상 비는 곳만 자른다. 화자분리·전사는 이어 붙인 오디오로 하고, 시각은 오프셋 표로 원본 기준으로 되돌린다. `meta.trim`에 임계값·잘라낸 구간·오프셋 표.
    - 360분 녹음 실측: 녹음기 "무음"은 0이 아니라 -50〜-57dB 잡음, 말소리 -10〜-25dB. 임계 -37dB로 1시간 56분만 남음. 잘라낸 구간을 2분씩 Whisper로 들어 보니 "다음 영상에서 만나요"류 환각뿐(말소리 없음).
    - 시끄러운 방은 잡음 바닥이 -40dB라 임계 상한을 -30dB로 둠(-35dB면 잡음을 말소리로 봄).
    - 백로그 4시간 초과 8개 중 확인한 4개(2026-10-30): 4:52→3:39, 6:00→1:56, 5:38→3:40, 4:13→3:13 — 무음을 빼면 모두 4시간 미만. 나머지 4개는 녹음기가 분리돼 아직 확인 못 함.
    - **자를 무음 길이(`--trim-min-gap <분>`, 기본 5분) 근거** (2026-10-30, 백로그 실녹취: 4시간 초과 긴 녹음 4건 합계 20:30, 회의만 있는 녹취 8건 합계 7:00). 무음 길이는 말소리 창 사이의 빈 1분 창 수에서 앞뒤 여유(15초씩)를 뺀 값.

      | 무음 길이 | <1분 | 1〜2분 | 2〜3분 | 3〜5분 | 5〜10분 | ≥10분 |
      |---|---|---|---|---|---|---|
      | 긴 녹음 4건 | 7 | 7 | 8 | 2 | 10 | 5 |
      | 회의 녹취 8건 | 6 | 2 | 0 | 0 | 0 | 0 |

      | 기준 | 1분 | 2분 | 3분 | **5분** | 10분 |
      |---|---|---|---|---|---|
      | 긴 녹음 4건: 남는 길이 | 11:49 | 11:59 | 12:19 | **12:27** | 13:44 |
      | 회의 녹취 8건: 잘리는 길이 | 3분(2곳) | 0 | 0 | **0** | 0 |

      - 회의 안의 침묵은 2분을 넘지 않았다. 1분 기준이면 회의 2건에서 1분 30초씩 잘리는데, Whisper로 들어 보니 한 곳은 작게 말한 맞장구와 짧은 의견이 들어 있었고, 다른 곳은 앞뒤 45초가 모두 같은 발표 중이었다 → 1분은 회의 내용을 잃는다.
      - 2〜3분 기준은 회의에서는 잘리는 게 없지만, 긴 녹음에서 더 줄어드는 시간이 5분 기준보다 8〜28분(4건 합계)뿐이다. 그만큼 회의 중 긴 침묵(자료 읽기, 발표 준비)을 자를 위험을 지는 셈이라 득이 작다.
      - 10분 기준이면 긴 녹음에서 1시간 17분을 더 처리한다(local 실시간 12배 가정이면 약 6분). 5분 기준에서만 잘리는 5〜10분 무음 10곳의 약한 소리 창과 앞뒤 45초를 들어 보니 9곳은 무음 환각("다음 영상에서 만나요"류)이었고, 1곳은 회의가 끝난 뒤 사적 대화로 보이는 작은 말소리가 있었다(`meta.trim.review`에 잡힘).
      - 결론: 기본 5분 유지. 회의 중간이 잘릴까 걱정되는 녹음은 `--trim-min-gap 10`, 놓친 말소리가 아까우면 `--no-trim`. 회의 녹취 표본이 8건이라 회의 중 3분 넘는 침묵이 흔한 유형(시험·필기 등)이 나오면 다시 본다.
  - dry-run은 파일 길이와 함께 추정 말소리 길이를 보여 주고, 무음을 빼고도 6시간(`MAX_SEC`)이 넘는 파일만 "분할 필요"로 건너뜀(청크 분할 + 청크 간 화자 맞추기는 위시리스트, 보류).
  - **긴 녹음 메모리 실측** (2026-10-30, studio 64GB, 말소리가 빽빽한 회의 녹취 8건을 이어 붙인 입력). 한도를 4시간에서 6시간으로 올린 근거. 메모리는 RSS + torch MPS 드라이버 할당 + mlx 메모리의 최대값.

    | 입력 | 단계 | 최대 메모리 | 시간 | 군집화 임베딩 수 n |
    |---|---|---|---|---|
    | 1시간 | 화자분리만 | 5.0GB | 124초 | 3,722 |
    | 2시간 | 화자분리만 | 5.6GB | 240초 | 7,295 |
    | 3시간 | 화자분리만 | 6.0GB | 390초 | 11,259 |
    | 4시간 | 화자분리만 | 6.5GB | 500초 | 15,089 |
    | 6시간 | 화자분리만 | 7.6GB | 738초 | 22,539 |
    | 6시간 | `rec2md` 전체(무음 자르기·화자분리·전사·목소리 DB) | 약 21GB | 1,985초(화자분리 804 + 전사 1,167) | - |

    - 메모리는 거의 선형이다. 모델·MPS 고정분이 약 3.5GB이고, 나머지가 시간당 약 0.5GB씩 는다. VBx 군집화의 `linkage`는 n²이지만 n이 대략 말소리 1초당 1개(한 화자만 말하는 구간만 씀)라 6시간에도 거리 행렬이 약 2GB, 시간은 26초다.
    - 전체 실행의 메모리 21GB는 RSS 5.6GB와 Metal(GPU) 할당 15.4GB를 더한 값이다. torch의 `driver_allocated_memory`는 프로세스의 Metal 할당 전체라 mlx 몫도 들어 있다(2GB를 mlx로 잡자 torch 값도 2GB가 됨). 그래서 둘을 따로 더하면 겹쳐 센다(그렇게 센 값은 29GB). Metal 15.4GB 중 약 10GB는 mlx 버퍼 캐시(최대 활성 2.4GB, 캐시 포함 12.3GB)다. 이 캐시는 아래처럼 전사 중 1GB로 묶었다.
    - 6시간 전체 처리는 약 33분(실시간 약 11배)이다.
    - **mlx 캐시 상한** (2026-11-04, 같은 종류의 빽빽한 입력 1시간, 화자분리로 구한 말소리 구간 132개·57분을 전사만 따로 돌림). local 엔진은 전사하는 동안 `mx.set_cache_limit(1GB)`를 걸고, 끝나면 캐시를 비우고 원래 상한으로 돌린다.

      | 캐시 상한 | 최대 mlx 메모리(활성+캐시) | 최대 캐시 | 전사 시간 | 기준 대비 글자 차이 |
      |---|---|---|---|---|
      | 없음(mlx 기본) | 9.1GB | 7.5GB | 254초 | 기준 |
      | 없음(다시) | 9.3GB | 7.7GB | 216초 | 6.0% |
      | 2GB | 3.7GB | 2.0GB | 214초 | 5.1% |
      | **1GB** | **2.7GB** | **1.0GB** | **198초** | 2.4% |
      | 0(캐시 끔) | 2.3GB | 0 | 225초 | 4.7% |

      - 활성 메모리 최대치는 모두 2.4GB로 같다. 늘어나던 것은 캐시뿐이다.
      - 전사 시간은 같은 설정을 다시 돌려도 254초와 216초로 갈렸다. 상한을 걸어도 느려지지 않았다.
      - 결과 텍스트는 상한이 없는 같은 설정끼리도 6% 다르다(온도 폴백 디코딩이 실행마다 달라짐). 상한별 차이(2.4〜5.1%)는 그 편차 안이다.
      - 6시간 전체 실행의 Metal 15.4GB 중 약 10GB가 이 캐시였으므로, 상한을 걸면 전체 최대치는 약 12GB로 줄 것으로 본다(6시간은 다시 재지 않음).
    - 녹음기 최장 파일이 6시간이라 백로그는 무음을 자르기 전 길이로도 전부 한 번에 처리된다. 그래서 청크 분할은 보류했다.
- `REC000NN` 파일: 요약 기반으로 `YYYYMMDD_주제-RECnnnnn` 제목을 제안하는 `index.md` 생성. 실제 파일명 변경은 사용자 확인 후. → `rec2md index` (`index.py`, `cmd_index.py`, 2026-11-04)
  - 분업: CLI가 기계적 칸(길이·말소리 길이·회의 구간·화자 수·REC 번호·원본 지문·이름의 날짜·REC 앞뒤 앵커·번호 중복·날짜 단서 위치)을 채우고, 에이전트가 날짜(정밀도·확신도·근거)·주제·참석자 유형·한 줄 요약을 `index set`으로 채운다(SKILL.md 6단계). 다시 돌려도 판단·승인은 남는다. 항목은 원본 파일명으로 맞추고, 원본 지문(크기 + 앞뒤 1MB sha1)이 바뀌면 `stale`.
  - 날짜 단서(`clues`): "N월 N일"·연도·요일·상대 표현·회차를 정규식으로 위치만 찍는다. "N월 N일 X요일"이면 맞는 연도 후보를 붙인다. 발화 문맥을 담으므로 index.json에만 두고 index.md에는 에이전트의 근거 요약만 쓴다. 파일 수정일(1601년)은 쓰지 않는다.
  - REC 번호는 식별자가 아니다: 녹음기는 정확히 `RECnnnnn.MP3`인 파일만 보고 다음 번호를 정해, 이름을 바꾼 파일의 번호를 다시 쓴다. 번호 순서는 앵커 단서로 쓰되 번호가 겹치면(`rec_dup`) 약한 단서.
  - 파일명 날짜 표기: 모르는 자리는 `x`(`202610xx`, `2026xxxx`, `xxxxxxxx`) — Windows 파일명에 `?`를 못 쓴다. 일 단위는 확신도 high일 때만. 표기는 `index.format_name()` 한 곳에서 정한다(사용자 확인 중, 바뀌면 여기만 고침).
  - 이름 바꾸기 `rec2md index rename`: 기본 dry-run, 승인(`index approve`)된 항목만, 전사 출력 파일만 바꾼다(batch 상태 파일 키는 원본 이름 그대로 둬서 다시 전사하지 않음). 녹음 원본에는 쓰지 않고, `--copy-media <폴더>`일 때만 새 이름의 사본을 만든다(원본 폴더면 거부, sha1 검증). 이름 겹침·Windows 금지 문자·길이(150바이트)·stale이면 그 항목을 건너뛰고, `.rec2md-renames.json` 기록으로 `--undo`.
- 비용: 백로그는 studio local로 처리(추가 비용 없음, 처리시간은 파일럿 실측 후 산정). 참고로 RTZR로 전부 돌리면 188시간 ≈ 18〜19만원.

## 파일럿 결과 (2026-10-16, studio M2 Max, local vs 클로바노트)
클로바노트 txt 내보내기를 기준점으로 사용(`scripts/compare.py`, 파서 `rec2md.clova_txt`). 클로바도 정답이 아니므로 CER은 "두 엔진 간 차이"다.

| 녹취 유형 | 길이 | 클로바 화자 | local 화자 | 화자 일치율 | CER |
|---|---|---|---|---|---|
| 전화(2인) | 9분 | 2 | 2 | 95.5% | 20.1% |
| 회의(4인, 근접) | 38분 | 4 | 4 | 96.2% | 25.5% |
| 회의(5인, 근접) | 50분 | 5 | 5 | 92.6% | 28.4%* |
| 회의(11인, 원거리·대회의실) | 75분 | 11 | 15 | 70.2% | 52.6% |
| 위원회(9인 발언, 회의 테이블) | 68분 | 9 | 10 | 98.2% | 23.9% |

\* VAD 청킹 이전 수치

- 근접 녹음은 내용이 사실상 같다. CER 차이는 숫자 표기("1 2 3"/"1, 2, 3"), 말 반복("우리가 우리가") 유지 여부, 화자 전환 지점의 단어 1〜2개 귀속에서 주로 나옴. 고유명사는 양쪽 다 틀리는 편(local이 맞힌 경우도 있음: "2첨단").
- 9인 위원회(테이블 위 녹음기)는 근접 회의 수준: 남는 화자 1개는 21초짜리 조각. 원거리 약점은 인원수보다 마이크 거리 문제로 보임. 오인식은 고유명사·신조어(서비스명)에 몰림.
- 원거리 다화자 회의가 약점: 화자 과분할(11→15), 오인식 많음. 이 유형은 클로바/rtzr 보조 대상 후보.
- **VAD 청킹 도입 이유**: 파일 통째 전사 시 원거리 회의에서 Whisper가 문장을 대량으로 건너뜀(분량 클로바 대비 90% → 청킹 후 102%). 화자분리가 찾은 말소리 구간을 2초 미만 간격이면 합쳐 25초 이하 청크로 전사.
  - 합치는 간격 0.5초일 땐 짧은 청크가 많아 전사가 2.8배 느려짐(짧아도 30초 창 비용). 2초로 늘려 원래 속도 근처로 회복.
- 모델: large-v3(비turbo)는 청킹 시 품질 차이가 미미하고 1.4배 느려 기본은 turbo 유지(`--model`로 변경 가능).
- 처리속도(화자분리 포함): 근접 회의 38분 → 약 3분(실시간 12배). 188시간 백로그 ≈ 16시간 추정.
- 클로바노트 구버전 txt 중에는 전사가 아닌 요약본(주요 주제/다음 할 일/요약) 내보내기가 있음 → 비교 불가.

### 맥락 보정 1차 (2026-10-30, 회의 5인 근접 50분, 같은 시리즈 2회차)
용어집은 1회차에서 얻을 수 있는 것(참석자 5명 + 용어 21개)으로 만들고 2회차에 적용했다. 안건 조건은 2회차 안건에 나올 법한 용어 16개를 더한 것이다(프롬프트 상한 200토큰에서 일부 잘림).
정답(gold)은 클로바에서 사용자가 직접 붙인 참석자 화자명 5명뿐이다(n=5, 등장 29회 어림). 명부 확인은 하지 않았다. 등장 횟수는 시스템 중 가장 많이 맞게 적은 횟수로 어림한 값이다(`scripts/eval_terms.py`).

| 조건 | 참석자 인명 적중 | 보정 후보 첫 제안을 다 받아들였을 때 | CER(클로바 대비) | 보정 후보 수 |
|---|---|---|---|---|
| 기본(프롬프트 없음) | 38% | 86% | 25.1% | 159 |
| 1회차 용어집 프롬프트 | 97% | 97% | 25.1% | 133 |
| + 안건 용어 프롬프트 | 93% | 97% | 25.6% | 139 |
| 클로바노트 | 52% | - | 기준 | - |

- 프롬프트는 인명 표기를 크게 바로잡고 일반 CER은 그대로였다. 무음 구간에 프롬프트가 그대로 튀어나오는 환각은 없었다(프롬프트 항목이 여럿 들어간 세그먼트를 직접 확인했고, 모두 실제 발언이었음).
- 안건 용어를 더하면 그 용어만 맞게 나오기 시작했고(정책 약어 등 0→4회), 대신 인명이 약간 떨어지고 CER이 0.5%p 늘었다. 프롬프트가 길어질수록 희석되는 것으로 보인다 → 참석자·확정 용어를 앞에 두는 현재 순서를 유지한다.
- 클로바노트도 인명은 자주 틀린다(참석자 한 명은 클로바·기본 local 모두 0회). 시리즈 용어집이 클로바보다 나은 지점이다.
- 확률만 낮은 후보는 0.5 기준으로 50분에 529건이라 에이전트가 볼 수 없는 양이었다 → 가까운 용어가 없으면 0.2 미만만 후보로 올린다.
- 사람 판정 정답(gold v1)은 `scripts/term_cases.py` → `rec2md review --queue` → `eval_terms.py --cases --answers`로 이어서 만든다(사례 30건 준비).

**같은 시리즈 3번째 녹취**: 위원회 협의 회의, 64분(회의 구간 50분, 뒤 15분은 통화·잡담). 용어집은 1·2회차 지식(참석자 6명 + 용어 37개, 2회차에서 본 오인식 매핑 2개 포함). gold = clova-manual 화자명 9명 중 본문에서 이름이 불린 5명(등장 20회 어림). 나머지 4명은 어느 시스템에도 이름이 나오지 않아 분모에서 뺐다. 명부 확인은 하지 않았다.

| 조건 | 인명 적중 | 보정 후보 첫 제안을 다 받아들였을 때 | CER 회의 구간 | CER 전체 |
|---|---|---|---|---|
| 기본 | 55% | 100% | 22.1% | 23.5% |
| 1·2회차 용어집 프롬프트 | 100% | 100% | 22.5% | 26.4% → 24.2%* |
| 클로바노트 | 60% | - | 기준 | 기준 |

\* 2〜4토큰 디코딩 루프 정리(`clean.collapse_ngram_loops`) 전 → 후. 프롬프트 조건의 회의 뒤 구간에 두 토큰이 번갈아 55회 반복된 세그먼트가 하나 있었다(회의 뒤 구간 CER 53%→36%). 프롬프트 반향은 아니다. 회의 구간에는 루프가 없어 정리 전후가 같다.

- **권고**: `--series`·`--context`를 줬을 때 `initial_prompt`를 기본으로 켠다. 녹취 2건 모두 인명 적중이 크게 올랐다(38→97%, 55→100%). 대가로 **회의 구간 CER은 +0.4〜0.5%p 늘어난다**. 프롬프트는 참석자·확정 용어 위주로 짧게 둔다.

### 화자 목소리 DB 평가 (2026-10-30, `scripts/eval_voices.py`)
gold = clova-manual(사용자가 클로바에서 직접 붙인 실명, 사용자 확인). 녹취 5건(전화 9분, 근접 회의 38·50분, 위원회 68분, 회의 50분*), 화자 16명 / 정답 클러스터 25개, 이 중 두 녹취 이상에 나온 사람 5명. "미지정"·"성함 확인 필요" 라벨은 정답에서 뺐다. 순도 기준(우리 클러스터와 클로바 화자가 서로 70% 이상 겹침)에 못 미쳐 뺀 클러스터 2개(각 1분 남짓).
leave-one-out: 녹취 하나를 빼고 나머지의 정답 클러스터(30초 이상)를 등록한 뒤 뺀 녹취의 클러스터 전부를 매칭.

| 임계값 | 태깅 | 맞음 | 오태깅 | 미태깅(등록된 사람) |
|---|---|---|---|---|
| 0.50 | 17 | 14 | 2 (+정답 없는 클러스터 1) | 0/14 |
| 0.60〜0.65 | 15 | 14 | 1 (6.7%) | 0/14 |
| **0.70〜0.80** | 14 | 14 | **0** | **0/14** |
| 0.85 | 13 | 13 | 0 | 1/14 |
| 0.90 | 8 | 8 | 0 | 6/14 |

\* 회의 뒤 통화·잡담이 이어진 녹취라 회의 구간(0〜49:40)만 평가(`--bounds`).

- 점수 분포: 같은 사람 최저 0.848(14쌍), 다른 사람 최고 0.664(310쌍). 기본 임계값은 오태깅을 먼저 막도록 두 분포 가운데인 **0.75**, 0.75〜0.80은 `이름?`로 표시.
- 등록 방식(클러스터 중심 vs 중심에서 먼 구간을 뺀 구간 임베딩 평균)은 이 데이터에서 차이가 거의 없다. 섞임에 대비해 강건 방식을 기본으로 둔다. 정답 클러스터의 등록 순도는 0.88 이상이라 경고 기준 0.8은 깨끗한 클러스터에서 울리지 않는다. 같은 사람이어도 3초 미만 구간은 중심에서 멀게 나오는 일이 많다.
- 안전장치(2026-10-30): ① 이미 등록된 사람에 임베딩을 더할 때 기존 것과의 유사도가 0.75 미만이면 거절(`--force`로 강제). 근거: 같은 사람의 녹취 간 등록 벡터 최저 0.830(14쌍), 다른 사람끼리 최고 0.653(120쌍). ② 붙은 사람과 다음 사람의 점수 차가 0.15 미만이면 `이름?`. 근거: 맞게 붙은 14개의 차는 최저 0.263(10퍼센타일 0.322). 두 장치를 넣고 다시 잰 leave-one-out은 태깅 14, 오태깅 0, `이름?` 0으로 그대로다.
- 원거리 등록 위험: 원거리 대회의실 녹취(75분, 화자 15)에서 본인 후보 클러스터는 근접 등록 임베딩과 0.44〜0.52라 자동 태깅되지 않았다(오태깅도 없음). 이를 본인으로 더하면 근접 녹취에서 본인이 아닌 화자의 본인 점수 최고가 0.516 → 0.645로 오르고, 같은 방 다른 화자들도 그 임베딩에 0.60〜0.64가 나왔다. 목소리보다 방·마이크 특성을 닮는 것으로 보이므로 ① 장치가 이런 등록을 막고, 꼭 필요하면 사용자 확인 후 `--force`로만 넣는다.

### 회의 구간 추정 1차 (2026-10-30, `rec2md bounds`, `src/rec2md/bounds.py`)
녹음기를 늦게 켜거나 안 꺼서 앞뒤에 붙은 잡담·통화를 `meta.meeting_bounds`에 후보로 남긴다. 신호는 종료·개회 표현, 발화 밀도 하락, 화자 구성 변화(한 화자 독차지, 말하는 사람 수 급감, 회의 화자 비중 하락), 긴 무음이다. 창 신호는 경계보다 늦게 잡히므로 종료 표현이 있으면 그 발화 끝으로 당기고, 최고점의 80% 이상인 후보 중 회의에 가장 가까운 시각을 고른다.

| 검증 | 건수 | 결과 |
|---|---|---|
| 실녹취, 회의 뒤 통화·잡담 15분 붙음(정답은 사용자 확인) | 1 | 끝 오차 0초(high) |
| 실녹취, 끝까지 회의(전화·회의 2〜15인, 9〜75분) | 7 | 7건 모두 자르지 않음 |
| 반합성: 실녹취 회의 뒤에 다른 녹취 이어붙임 | 4 | 4건 모두 오차 3초 이내 |
| 반합성: 회의 앞에 통화·잡담 이어붙임 | 2 | 1건 오차 0초, 1건 놓침(개회 표현 없음) |

- 놓친 경우(1건)는 "자르지 않음" 쪽이다. 시작 쪽은 개회 표현이 없으면 기준을 높였다(회의 초반 발표로 화자가 쏠려 4분, 1분을 잘라 낸 오탐이 2건 있었음).
- 반합성은 이어붙인 녹취의 화자 라벨이 회의와 겹치지 않아 "회의 화자 비중" 신호가 실제보다 강하게 나온다. 실제 연속 녹음에서는 통화하는 사람이 회의 화자 라벨을 그대로 가질 수 있다.
